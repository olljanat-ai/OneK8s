# Portainer on AKS, agents everywhere else

Portainer **Business Edition** is the platform's fleet console: one server, on
the same AKS cluster that runs the Argo CD hub, showing all four clusters.
`foundations/azure/portainer.tf` deploys the server and publishes it on
`https://portainer.onek8s.lol`; the `portainer/` stack registers EKS, GKE and
OKE with it and installs an **Edge Agent** on each of them.

It sits next to Argo CD rather than overlapping with it. Argo CD is how the
platform *deploys* — desired state in Git, reconciled onto every cluster.
Portainer is how an operator *looks at* what is running, on any cloud, without
four kubeconfigs and four `aws eks update-kubeconfig`-shaped incantations.
Nothing here deploys workloads; the `AppProject` boundaries in
[argocd.md](argocd.md) are still what governs that.

```
                       ┌──────────────── AKS (foundations/azure) ───────────────┐
 portainer.onek8s.lol  │                                                        │
  :443 ───────────────▶│  Traefik ──HTTP:9000──▶ portainer                      │
  (A record, out       │      │                     │  cluster-admin SA:        │
   of band)            │      │                     │  manages THIS cluster     │
  :8000 ──────────────▶│  IngressRouteTCP ─────────▶│  :8000 edge tunnel        │
                       │      ▲                     │  /data PVC (its database) │

   ┌────┴─────┐            ┌──────────┐          ┌─────┴────┐
```

## The hub manages itself

There is no agent on AKS. The Portainer chart binds its own ServiceAccount to
`cluster-admin` on the cluster it is installed in, so the hub appears in the UI
as the local environment from the first start. The other three clouds need an
agent precisely because Portainer is not running on them.

## Why Edge Agents

The standard Portainer agent is dialled *into*: the server opens a connection
to the agent's address. On EKS, GKE and OKE that means publishing an endpoint
with cluster-admin behind it on each cluster and keeping it reachable from
AKS — the platform's own ingress would be carrying a cluster-admin API on
three clouds.

The Edge Agent dials *out*. It polls the Portainer URL over HTTPS and, only
while an operator has that environment open, opens a reverse tunnel back to
the same host. Nothing on a spoke has to be reachable from anywhere, and the
entire credential is one **Edge key** — a base64 blob holding the Portainer
URL, the tunnel address, the tunnel server's fingerprint and the environment's
ID. Deleting the environment on the server invalidates it.

That key cannot be computed locally: it is generated by the server when the
environment is created. This is why the `portainer/` stack talks to the
Portainer API at all, rather than only to Kubernetes — and why it is a layer
of its own, applied after the server exists and its DNS record resolves.

## Why the tunnel rides on the ingress

Portainer derives the tunnel address from **the host of its own URL** plus its
tunnel port: an agent told to poll `https://portainer.onek8s.lol` will tunnel
to `portainer.onek8s.lol:8000`, and nowhere else. There is one A record, so
port 8000 has to answer on the same load balancer as port 443.

So the Azure foundation asks the shared ingress module for one extra Traefik
entrypoint (`extra_ports`) and renders an `IngressRouteTCP` next to it that
hands everything arriving on :8000 to the Portainer Service. Two consequences
worth knowing:

- The route object carries its own `metadata.namespace`, so Helm applies it
  **into the Portainer namespace** even though the Traefik release lives in
  `traefik`. That keeps the service reference same-namespace. The alternative,
  Traefik's `allowCrossNamespace`, would also let any tenant's `IngressRoute`
  reach into any other namespace — which is exactly the isolation this
  platform enforces everywhere else.
- The entrypoint is not TLS, so the route matches ``HostSNI(`*`)``: everything
  that reaches :8000 is tunnel traffic. The tunnel is a chisel
  (SSH-over-websocket) listener and is designed to be public — an agent
  authenticates with its Edge key and pins the server's fingerprint, both of
  which came from the key it was installed with.

With `enable_ingress = false` the entrypoint and the route are simply not
created, and the `portainer/` stack warns: agents still register and check in,
but no environment can be browsed.

## The licence, and the admin account

Both come out of the environment's **Key Vault**, next to the wildcard
certificate and the tenant secrets — nothing is typed into the UI on a
rebuild:

| Key Vault secret | Variable | What it does |
|---|---|---|
| `portainer-license` | `portainer_license_secret_name` | Passed to the server as `--license-key` at boot, so it comes up licensed |
| `portainer-admin-password` | `portainer_admin_password_secret_name` | Mounted by the chart and passed as `--admin-password-file`; creates the built-in `admin` account at first start |

The admin password is optional (`null` leaves the account to be created in a
browser within Portainer's setup window), but an unattended install sets it:
the `portainer/` stack authenticates as that account when it registers the
spokes.

Both are read at apply time, so a brand-new environment — where the same apply
creates the vault — bootstraps in two passes: apply with
`enable_portainer = false`, put the secrets in the vault, apply again. An
apply that cannot find the licence fails rather than installing an unlicensed
server.

The trade-off with `--license-key` is that the licence ends up in the Helm
release values, so in the pod's `argv` and in this stack's Terraform state. It
is a paid entitlement rather than an infrastructure credential — it grants
nothing in this platform — and the alternative is a licence screen on every
rebuild.

## What the `portainer/` stack does

One stack, one state file per environment, every cloud in one run — the same
shape as `tenants/` and `gitops/`, with the cloud as a key of `var.agents`:

```hcl
# portainer/envs/prototype.tfvars
agents = {
  aws = {}
  gcp = {}
  oci = {}
}
```

Per entry it creates a Portainer environment through the API (type `4`, "Edge
Agent"; Portainer flips it to `7`, "Kubernetes Edge Agent", once the agent
connects and identifies itself — the provider expects that and does not report
it as drift) and installs `modules/portainer-agent` on that cluster with the
`edge_id` / `edge_key` the server just generated.

It also owns the server's **settings**, because two of them are prerequisites
rather than preferences: Edge compute has to be enabled before an Edge
environment can be registered, and the Edge Portainer URL is what the server
tells agents to come back to. Portainer's settings API replaces the whole
object, so `settings = { enabled = false }` is there for an environment whose
Portainer settings (SSO, for one) are managed elsewhere — then those two have
to be set by hand.

Azure is never listed in `var.agents` (the hub manages itself), and a cloud
left out is untouched: no foundation state is read, no cluster is contacted,
its provider stays inert.

### Credentials

The `portainer` provider reads them from the environment, never from a
variable or a state file:

| Variable | |
|---|---|
| `PORTAINER_API_KEY` | an API token created in the UI (Account → Access tokens) |
| `PORTAINER_USER` + `PORTAINER_PASSWORD` | or the admin account the foundation bootstrapped |

In CI they are GitHub secrets, the same way every cloud credential is. The
endpoint is *not* configured: it comes from the hub foundation's
`portainer_url` output, so the stack cannot be pointed at the wrong server by
a stale variable.

## What the agent gets on each cluster

`cluster-admin`, bound to the agent's ServiceAccount — Portainer's own
published manifest, and what the product assumes. The agent is the operator's
hands on that cluster: it lists and edits every namespaced object, streams
logs, opens shells.

That is a wider grant than the `argocd-manager` ServiceAccount the Argo CD
spoke registration creates, and deliberately so: Argo CD applies a known set
of manifests, Portainer is an interactive console. `cluster_role = "view"`
narrows it and turns parts of the UI into errors rather than into a read-only
view — see [modules/portainer-agent/README.md](../modules/portainer-agent/README.md).

## Deploying

```bash
cd portainer
terraform init -backend-config=backend/prototype.hcl
terraform apply -var-file=envs/prototype.tfvars
```

Or **Actions → Deploy Portainer → environment `prototype`**, which binds to
the `portainer-prototype` GitHub environment.

Prerequisites, in order:

1. `foundations/azure` applied for this environment with
   `enable_portainer = true`, and the `portainer-license` secret in its Key
   Vault.
2. An A record for `portainer.onek8s.lol` pointing at the AKS ingress load
   balancer (`kubectl -n traefik get svc traefik`), like every other host
   here. This stack calls the API over that name, so unlike `gitops/` it does
   not work before DNS does.
3. The foundations of every cloud listed in `var.agents`.
4. `PORTAINER_API_KEY` (or `PORTAINER_USER`/`PORTAINER_PASSWORD`) in the
   environment.

## Operating

```bash
# Is the agent up, and what is it saying?
kubectl -n portainer logs deploy/portainer-agent --context <spoke>

# What did the server generate for this cluster?
terraform -chdir=portainer output environments

# The server's own logs (licence problems show up here first)
kubectl -n portainer logs deploy/portainer --context <hub>
```

An agent that will not connect is almost always one of four things: the DNS
record does not resolve from the spoke, :8000 is not published (the hub's
`portainer_edge_tunnel` output is null), the server's certificate cannot be
chained by the agent (`insecure_poll = true` is the escape hatch, and should
not be needed behind the platform wildcard), or the environment was deleted
on the server and the key is stale.

## Known gaps

- **The tunnel is public.** Port 8000 on the ingress load balancer is open to
  the internet, as an Edge tunnel has to be. It is authenticated by the Edge
  key and fingerprint-pinned, but it is one more listener with no IP
  allow-list in front of it.
- **Nothing rotates an Edge key.** Re-creating the environment issues a new
  one and the module rolls the agent onto it; that is the rotation path.
- **Sign-in is local.** The Argo CD UI is behind Entra ID; Portainer here is
  behind its built-in admin account. Portainer BE supports OAuth/OIDC, and
  wiring it to the same Entra tenant is the obvious next step — it would also
  let `settings.authentication_method` move off `1`.
- **One replica, one PVC.** The server is a single stateful pod. Its database
  holds the environments and their Edge keys, so the volume is the thing to
  back up (Portainer BE has scheduled S3 backups; nothing here configures
  them).
- **No agent is deployed by Argo CD.** The agents are Terraform's because
  their Edge keys are generated per cluster at registration time, which is not
  something a Git-committed manifest can carry.
